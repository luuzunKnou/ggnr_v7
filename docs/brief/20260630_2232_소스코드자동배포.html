배경

관공서·폐쇄망 환경에서는 중앙(GNMS 등)에서 받은 최신 소스 패키지를 각 현장 서버에 올리고 적용·재기동하는 자동 배포 흐름이 필요하다. dev 화면의 버전 관리·설치 ZIP·청크 업로드·적용 API 등이 구현되어 있으나, 실제 다운로드 → 업로드 → 압축 해제·반영 → 재시작 → 결과 확인 전 구간이 안정적으로 동작하는지 검증이 필요하다. 테스트 중 발견되는 오류·누락·안내 부족을 고쳐 운영·시연에 쓸 수 있게 기능을 정상화해야 한다.

활용

  1. 현장·운영 담당자가 GNMS(또는 배포 서버) 최신 버전을 조회·다운로드해 해당 서버 소스를 갱신한다.
  2. 클라이언트 PC가 중간망 역할을 할 때, 패키지를 받아 내부 서버로 전달·적용하는 중계 배포를 수행한다.
  3. 배포 후 재시작 옵션(프로세스 종료·서비스 재기동 등)과 적용 파일·건너뛴 파일 목록을 확인한다.
  4. dev «버전 관리» 등에서 한 번의 조작으로 배포·로그 확인이 가능해야 시연·긴급 패치에 활용한다.
  5. 향후 80포트 오케스트레이션(요청·패키지·리포트)과 같은 업로드·적용 패턴을 재사용할 수 있게 기반을 맞춘다.

필요 기능

  1. 최신 버전 메타 조회 — 버전명·파일명·크기·다운로드 경로 등이 없거나 깨진 경우 명확한 오류 안내.
  2. 패키지 다운로드 — ZIP 수신·저장·(선택) 무결성 검증. 대용량 시 청크 업로드·재개가 끊기지 않아야 한다.
  3. 워크스pace 적용 — 압축 해제·파일 복사 시 제외 목록·덮어쓰기 규칙 준수, 적용·건너뛴 파일 수·샘플 목록 표시.
  4. 재시작 — 사용자 선택(재시작 여부·방식)에 따라 재기동 신호·예약·결과 메시지가 일관되어야 한다.
  5. 진행·로그 — 다운로드·업로드·적용·재시작 단계별 진행 상태·로그를 화면에서 실시간 또는 완료 후 확인 가능해야 한다.
  6. 실패 처리 — 네트워크·디스크·권한·ZIP 손상 등 실패 시 어느 단계에서 실패했는지와 재시도 방법 안내.
  7. 설치 ZIP 내보내기·로컬 ZIP 적용 등 보조 경로도 동일 품질로 동작하는지 테스트·보완.
  8. dev·demo·prod 등 환경별 배포 정책(자동·승인) 차이는 plan에서 정의하되, 최소 dev에서 E2E 성공을 1차 목표로 한다.

참고·제약

  • 기존 버전 관리 UI·소스 버전 API·청크 업로드·GNMS 중계 클라이언트를 우선 테스트·수정한다.
  • 관공서 망: 클라이언트 중계·80포트 제약 — http 오케스트레이션 plan과 방향 일치, 1차는 단일 서버·dev E2E 정상화에 집중.
  • 배포 시 .env·런타임·node_modules 등 민감·대용량 제외 정책 유지.
  • 운영 prod 자동 배포·승인 워크플로는 2차; 1차는 기능 정상화·테스트 목록·오류 수정.
  • DB migrate·스키마 자동 적용은 사용자 명시 요청 전까지 배포 파이프에 넣지 않는다.
