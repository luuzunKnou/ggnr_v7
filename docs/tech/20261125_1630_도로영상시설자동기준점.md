## 1. 결론부터

**가능하고, 방향이 맞다.**  
수동으로 찍을 때 이미 «교량 앞·터널 입구·과속방지턱»처럼 **지도에 있는 시설**을 보고 시각을 맞추고 있다면, 그 작업을

1. 노선에 붙은 시설 → **노선 거리(m)**  
2. 영상에서 그 시설을 지나는 순간 → **영상 시각(초)**  
3. `(초, m)` 쌍 → 지금 수동 기준점과 **동일한 입력**

으로 자동화할 수 있다.  
사실 현재 분석기도 **교차시설·도로중심선교점**으로 비슷한 일을 일부 하고 있다. 그걸 **주요·안전·부대 시설**까지 넓히는 확장이다.

## 2. 지금 이미 하는 것 / 제안하는 것

| | 지금 | 제안(시설 자동 기준점) |
|--|------|------------------------|
| GIS 힌트 | 교차시설 면(`a0080000`), 도로중심선교점(`a9990001`) | + 교량·터널·과속방지턱·표지 등 **노선 조인 시설** |
| 영상 쪽 | 큰 **회전** 봉우리 ↔ 분기 m 짝맞춤 | + 시설별 **통과 이벤트**(어두워짐·요철·구조물 등장 등) ↔ 시설 m |
| 저장 형태 | 분기 보정 / 수동 `road_video_landmark` | 자동 생성 `(t, m)`을 수동점과 **같은 슬롯**에 넣거나, 분석 입력 `landmarks`·`manualLandmarksByPart`로 전달 |

사람이 하는 일:

> 지도에서 교량 위치 확인 → 영상 스크럽하다 교량 장면 → 그 시각 저장  

기계가 하는 일:

> 해당 RDID 노선의 교량 geom → 노선 위 m → 영상에서 «교량 통과» 시각 추정 → `(t, m)`

## 3. 쓸 수 있는 시설 (도로대장에 이미 있는 레이어)

도로대장 상세 버튼에 묶인 레이어 예 (`roadLedgerDocLayerMap`).

| 구분 | 예시 레이어 | 자동 기준점 적합성 | 이유 |
|------|-------------|-------------------|------|
| 주요시설 | 교량 `a0070000`, 터널 `a0110020`, 육교·지하차도·고가 등 | ★★★ | 희소·영상에서 티가 큼, 사람이 제일 많이 씀 |
| 기하구조 | 교차시설·중심선교점 (이미 사용) | ★★★ | 회전·로터리와 맞음 |
| 부대/안전 | 과속방지턱 `c9530003`(부대 쪽 코드), 표지·신호 등 | ★★☆ | 방지턱은 요철·시선 변화로 잡기 좋음. 가로등·표지는 **너무 촘촘**하면 짝이 꼬임 |
| 기타 | **측점 `a9990013`**, **거리표 `a9990012`** | ★★★ (m) / ★★ (t) | m은 즉시·촘촘. t는 거리표·보이는 측점 표식부터 |
| 배수·기타 | 옹벽·측구·점용 등 | ★☆ | 영상 단서가 약하거나 노선과 애매 |

**추천 1차 대상(사람이 찍던 것과 동일):**  
교량 · 터널(입·출구) · 과속방지턱 · **측점** · (있으면) **거리표** · (기존) 교차·분기  
그다음: 육교·지하차도·신호등(삼거리급만) · 주요 표지

노선과의 연결은 기존과 같이 **RDID 16자 조인**(총괄↔시설) + geom을 노선 선형에 **투영한 m**이면 된다.  
면형(교량·터널·방지턱)은 중심 또는 노선과 겹치는 구간의 **진입 m / 진출 m** 두 점으로 쓸 수 있다.

### 3.1 측점·거리표 — 특히 유리한 점

도로대장 **기타시설**에 이미 있다.

| 레이어 | ID | 형태 | 비고 |
|--------|-----|------|------|
| 측점 | `a9990013` | POINT | 목록 표시 필드 `SECT_ST`(위치시점). 노선을 따라 촘촘한 측점열 |
| 거리표 | `a9990012` | POINT | km 표지. 영상·도로변에서 비교적 잘 보임 |

**왜 시설 자동 기준점에 넣기 좋은가**

- 수동으로도 «이 측점/거리표 지점»을 보고 찍는 경우가 많음 → 업무 습관과 일치  
- **절대 m이 GIS에 바로 있음** (점을 노선에 투영하면 끝). 교량보다 훨씬 촘촘하면 사이 구간 드리프트를 자주 잡아 줌  
- 측점 간격이 대략 일정하면, 강한 앵커(교량·터널) 사이에서 **시간 비율 ↔ 측점 m**으로 스케일을 보정하기 좋음  

**주의 (영상 시각 t 쪽)**

- 측점은 **지도에는 많지만**, 360 영상에서 매 측점 표식이 항상 또렷하지는 않음 (간격 짧으면 OCR·검출이 어려움)  
- 그래서 역할을 나누는 편이 현실적임:  
  - **측점:** 우선 **m 격자**(스케일·구간 보정·후보 앵커). 표식이 영상에서 잡히면 t까지 짝맞춤  
  - **거리표:** 표지판·숫자 OCR 또는 검출로 **t 짝**을 노리기 쉬움 (개수는 적음)  
- 과밀하면 분기와 같이 **최소 이격**으로 솎거나, «교량 사이 N개만» 쓰는 식의 신뢰도 게이트가 필요  

정리: **측점 포함은 가능하고 권장.**  
특히 «시설 이벤트 ↔ t»가 약한 구간에서 **m 앵커 밀도**를 올려 주는 역할을 한다.

## 4. 자동화 두 갈래 (핵심)

시설 GIS만 있으면 **m은 바로** 나온다. 어려운 쪽은 **영상 시각 t**다.

### 방법 A — GIS m만 쓰고, 영상은 “이벤트”로 t 추정 (현실적 1차)

시설 종류별로 영상에서 잘 나오는 **통과 신호**를 정의한다.

| 시설 | 영상에서 잡을 수 있는 신호 예 |
|------|------------------------------|
| 터널 | 밝기 급감→암전→급증 (입구/출구 두 이벤트) |
| 교량 | 난간·하부 공간·수평선 변화, 또는 구조물 실루엣(검출기) |
| 과속방지턱 | 짧은 시간 피치/화면 상하 흔들림, 노면 횡단 패턴 |
| 교차·분기 | 이미 쓰는 **큰 yaw** (현행) |

알고리즘 흐름:

1. 노선 시설 목록 → `[(종류, route_m), …]` (최소 간격으로 솎기)  
2. 영상 전 구간 이벤트 목록 → `[(종류, time_sec), …]`  
3. **같은 종류**끼리 순서 보존 매칭 (DTW/탐욕 + 시간·거리 비율 제약)  
4. 짝이 확실한 것만 `(t, m)` 채택 → 분석기 `_align_by_landmarks` / `_align_by_manual_times`와 **동일 입력**

장점: 시설 DB만 있으면 되고, 수동과 같은 “종류 단서”를 씀.  
주의: 이벤트가 없거나(주간 터널 짧음, 방지턱 GIS만 있고 실제 완화됨) 오검출이면 짝이 빗나감 → **신뢰도 낮은 짝은 버림**.

### 방법 B — 딥러닝/템플릿으로 “이 장면 = 이 시설” (2차)

프레임 임베딩·객체검출로 교량/터널/방지턱을 인식하거나,  
과거 조사 영상과 매칭. 절대 단서는 더 강하지만 구축 비용↑.

1차는 **A**, 막히는 종류만 B를 얹는 구성이 맞다.

### 방법 C — m만 강제 (약한 형태, 이미 분기에 가까움)

시각 이벤트 없이 GIS m만 `landmarks` 배열에 넣고,  
현행처럼 “큰 회전 시각”과만 짝맞춤.  
교량·방지턱은 **회전이 약해서** 분기만큼 잘 안 붙을 수 있음.  
그래서 **종류별 이벤트(A)** 가 필요해진다.

## 5. 기존 파이프라인에 넣는 위치

```
스케줄러 analyzeVideo
  ├─ loadRoadVideoRoute
  ├─ loadRoadVideoCrossingZones      ← 유지
  ├─ loadRoadVideoBranchLandmarks    ← 유지
  └─ [신규] loadRoadVideoFacilityLandmarks(roadKey)
           → [{ type, routeM, enterM?, exitM? }, ...]
                 │
Python fit_to_route
  ├─ DTW 초안
  ├─ 분기 보정 (_align_by_landmarks)
  └─ [확장] 시설 이벤트↔m 매칭 → _align_by_manual_times 와 같은 강제/구간 재매핑
                 │
결과: 지금과 동일한 1초 anchor
```

화면의 수동 기준점은 **남는 불확실 구간만** 보완.  
자동으로 잡힌 점은 지도에 «자동(교량)»처럼 구분해 검수하게 할 수 있다.

## 6. 왜 이게 HMM보다 “수동 대체”에 가깝나

수동점의 본질은 알고리즘 이름이 아니라 **(지도상 절대 m, 영상상 절대 t)** 한 쌍이다.  
시설 레이어는 **절대 m 창고**이고, 영상 이벤트는 **절대 t 후보**다.  
둘을 이어 주면 사람이 하던 기준점 작업을 기계가 대신하는 것이다.

HMM/DTW는 그 사이 **빈 구간을 채우는** 역할.  
시설 자동점은 **채우기 전에 못을 박는** 역할 → 정확도·무수동에 더 직결.

## 7. 실패·주의할 점

| 이슈 | 대응 |
|------|------|
| 같은 종류가 짧은 간격으로 여러 개 | 최소 이격(예: 80~150m), 매칭 시 순서·시간비율 제약 |
| GIS는 있는데 영상 이벤트가 약함 | 그 점은 버리고 DTW에만 맡김 (억지 짝 금지) |
| 면형 시설이 김(긴 터널·교량) | 입구 m / 출구 m 두 기준점 |
| RDID 조인 누락·위치 어긋난 시설 | 노선 버퍼 밖·투영 거리 큰 것 제외 |
| 가로등·표지처럼 과밀 | 1차 대상에서 빼거나 “삼거리 근처만” |
| 상·하행 | 시설 m은 노선 시작 기준 공통, 진행 방향만 reverse 처리 (현행과 동일) |

## 8. 실현 가능성 판단

| 질문 | 답 |
|------|----|
| 시설 레이어와 합쳐 기준점 가능? | **가능. 이미 교차·분기에서 부분 구현.** |
| 과속방지턱·터널·교량도? | **1차 추천 대상.** 사람이 찍던 기준과 동일. |
| 완전 무수동? | 시설이 드문 긴 직선은 여전히 약함. 다만 **찍는 횟수·필요성 크게 감소**가 현실 목표. |
| 측점도? | **가능·포함 권장.** m 격자로 쓰고, 보이는 표식·거리표는 t 짝까지. |
| 당장 뭐부터? | ① 노선별 교량·터널·방지턱·**측점·거리표** → route_m 목록 적재  
| | ② 터널 밝기·방지턱 요철 등 **단순 이벤트** + (가능하면) 거리표 검출  
| | ③ 종류별 순서 매칭 → 기존 수동점 정렬 API로 재분석  
| | ④ 측점 m으로 앵커 사이 **스케일 재추정** |

구현 착수 시 brief/plan으로 대상 레이어·이벤트·신뢰도 폐기 규칙을 고정하면 된다.

## 9. 한 줄

> 시설 레이어 = 지도 기준점, 영상 통과 이벤트 = 시간 기준점.  
> 둘을 짝지으면 지금 수동으로 찍던 방식 그대로 자동화할 수 있고,  
> 도로대장에 교량·터널·과속방지턱 레이어가 이미 있으므로 **가장 현실적인 정확도 개선 경로**다.
