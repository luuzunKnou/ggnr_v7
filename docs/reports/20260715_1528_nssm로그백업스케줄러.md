# 결과보고서

2026-07-15 | 200BingSu | nssm 로그 백업 스케줄러

## 목적

서비스(nssm)로 쌓이는 일일 로그를 자정에 백업 폴더로 옮기고, 원본은 비워 당일 로그를 이어 쓰게 한다. 개발 기동(npm run dev ~)에서는 돌지 않고 운영 기동(npm run start ~)에서만 등록한다.

## 요약

매일 0시에 `C:\logs`의 서비스 표준·오류 로그를 `backup`으로 복사한 뒤 원본은 삭제하지 않고 비운다. nssm 핸들과 로그 보기 창이 같은 경로를 유지하게 했다. 기동이 운영(`start`)일 때만 타이머를 걸고, 끌 때는 환경 변수로 끌 수 있다. 로그 보기 bat은 연결이 끊기면 다시 붙도록 바꿨다.

## 파일수정

추가 | src/integrations/nssmLogBackupScheduler.ts
 `rotateNssmServiceLogs` — backup 폴더 확인·생성 후 어제 날짜 접두로 복사하고 원본은 0바이트로 비움
 `startNssmLogBackupScheduler` — 매일 0시 슬롯만 실행. 기동이 운영이 아니면 등록 생략

 `register` — nssm 로그 백업 스케줄러 등록. 끌 때는 DISABLE_NSSM_LOG_BACKUP_SCHEDULER=1

수정 | open_ggnr_logs.bat
 로그 창 — Get-Content 끊기면 대기 후 재접속하는 루프로 변경

## 테스트

1. 운영 기동(`npm run start`) 후 콘솔에 nssm 로그 백업 스케줄 등록 안내가 나와야 한다.
2. 개발 기동(`npm run dev`) 후에는 해당 스케줄이 등록되지 않거나 skipped 안내가 나와야 한다.
3. 수동으로 백업 함수를 돌리거나 0시 근처에 두면 `C:\logs\backup`에 `어제날짜_GGNR_V7_stdout.log` 형태 파일이 생겨야 한다.
4. 백업 후 `C:\logs\GGNR_V7_stdout.log`는 남아 있고 내용이 비어 있어야 한다.
5. 서비스가 계속 돌아가는 동안 새 로그가 같은 파일에 다시 쌓여야 한다.
6. `open_ggnr_logs.bat`으로 연 창이 초기화 후에도 오류로 죽지 않고 이어서 보여야 한다.
7. DISABLE_NSSM_LOG_BACKUP_SCHEDULER=1 이면 스케줄이 등록되지 않아야 한다.
